# V4L2 路线重排（从零到岗位能力）

> 适配你的目标岗位：Linux 视频编解码驱动 + 软件栈适配 + 性能优化。  
> 这份路线只做一件事：告诉你“现在该学什么，先后顺序是什么，做到什么算过关”。

---

## 0. 先给你结论（你现在应该怎么学）

你现在不要“广撒网”。按这条主线走：

1. 先吃透用户态 V4L2 采集（single-planar + MMAP）
2. 再补 Media Controller、控制项、多线程和性能统计
3. 再进 DMABUF 与零拷贝思路
4. 再进 V4L2 M2M（编解码场景）
5. 最后进内核驱动（vb2、ioctl_ops、电源与恢复）

一句话：先会“调用和验证”，再会“驱动和优化”。

### 0.1 当前双环境调整（2026-06-02）

codec 学习现在明确拆成两条环境线：

1. `VM / x86 Linux`：主学 V4L2 M2M 通用模型。这里可以使用虚拟 M2M 节点训练 `OUTPUT/CAPTURE`、`QBUF/DQBUF`、`STREAMON/STREAMOFF`、`SOURCE_CHANGE`、`EOS/drain`，但它不证明实体 VPU 硬解能力。
2. `RK 板 / RK3568`：主验真实硬件路径。当前板端真实硬解走 RKMPP，例如 FFmpeg `h264_rkmpp` / `hevc_rkmpp`；如果没有 V4L2 M2M codec 字符设备，不要把 rkisp/camera 节点当 codec 节点。

执行入口：

```bash
less /usr/local/MPP_DEMO/rk3568_study_demo/v4l2/learning_plan/00_dual_environment_codec_route.md
```

新的判断标准是：

| 主题 | VM 负责 | RK 板负责 |
| --- | --- | --- |
| V4L2 M2M | ioctl/state machine/queue ownership | reality check，不强行硬解 |
| FFmpeg 软件路径 | 软件 baseline 和 API 学习 | 软件 baseline 对照 |
| FFmpeg 硬件路径 | 概念和可用后端对比 | RKMPP 真实硬解、性能、日志证据 |
| Debug report | 模型化 timeout/source-change 报告 | 板端 dmesg、backend、限制说明 |

## 2. 总路线图（12 周）

### 阶段 A（Week 1-2）：用户态采集基本功

目标：把采集链路写成可维护 API 层，不再是大 `main()`。

必学点：

1. `VIDIOC_QUERYCAP/S_FMT/REQBUFS/QUERYBUF/QBUF/DQBUF/STREAMON/OFF`
2. `select/poll` 等待模型
3. `bytesused/sizeimage/sequence/timestamp` 的意义
4. 错误码：`EINVAL/ENOMEM/EAGAIN/EIO`

必写代码：

1. `v4l2_open_device`
2. `v4l2_query_caps`
3. `v4l2_set_format`
4. `v4l2_init_mmap_buffers`
5. `v4l2_capture_one` 与 `v4l2_capture_loop`

过关标准：

1. 连续抓 300 帧稳定（无死锁）
2. 输出 fps、超时计数、dqbuf 失败计数
3. 任意一步失败时日志能定位到 ioctl 和参数

---

### 阶段 B（Week 3-4）：工程化与可观测性

目标：把“能跑”升级到“可调试、可复现、可回归”。

必学点：

1. 控制项：`QUERYCTRL/G_CTRL/S_CTRL`
2. 多线程采集与写盘分离
3. 日志分级和错误映射
4. 回归基线：固定分辨率/格式下的指标对比

必写代码：

1. 控制项模块：`v4l2_ctrl_query/get/set`
2. 采集线程 + 消费线程（有界队列）
3. 结构化统计：每秒 fps、队列峰值、超时率

过关标准：

1. 修改亮度/曝光能在图像上验证
2. 多线程跑 10 分钟无崩溃
3. 留存一份“性能基线报告”

---

### 阶段 C（Week 5-6）：媒体拓扑与零拷贝思维

目标：从“一个 `/dev/videoX`”升级到“看懂整个媒体图”。

必学点：

1. Media Controller 基础（entity/pad/link）
2. single-planar vs multi-planar
3. DMABUF 的角色（跨模块共享 buffer）
4. cache 同步与一致性概念

必写代码：

1. 在代码里支持 `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`（至少识别流程）
2. 增加 DMABUF 学习样例（哪怕先只做框架）

过关标准：

1. 你能画出“传感器 -> ISP -> video node”的简图
2. 你能解释“为什么零拷贝能提性能”
3. 你能口述 mplane 与 single 的 API 差异

---

### 阶段 D（Week 7-8）：编解码业务入口（V4L2 M2M）

目标：进入岗位核心：不是只采集，而是编解码链路。当前按 VM 主学 V4L2 M2M 逻辑，RK 板只做 M2M reality check。

必学点：

1. V4L2 M2M 双队列模型（OUTPUT/CAPTURE）
2. 编码/解码节点数据流方向
3. H.264/H.265 码流基本结构（IDR/P/B、GOP）
4. 帧率、码率、延迟三者关系

必写代码：

1. VM：最小 M2M 例程或虚拟节点验证，重点是 `OUTPUT/CAPTURE` 和 ioctl 顺序。
2. VM：码流 payload 到 OUTPUT `bytesused` 的桥接训练。
3. RK 板：运行 Stage06 reality check，确认是否存在真实 M2M codec 节点。
4. 若 RK 板没有 M2M codec 节点：写明真实硬解切到 RKMPP，不把此项判定为失败。

过关标准：

1. 能说清 OUTPUT 队列和 CAPTURE 队列各放什么
2. 能跑通 VM 侧 M2M 状态机或虚拟节点实验
3. 能解释 VM 结果不等于实体硬件加速证据
4. 能在 RK 板报告里明确 `V4L2 M2M` 与 `RKMPP` 的分工

---

### 阶段 E（Week 9-10）：软件栈适配（ffmpeg + v4l2）

目标：贴近岗位“打通软件栈到 VPU”。当前 RK 板硬解主线写作 `ffmpeg + rkmpp`，V4L2 M2M 作为通用模型和其他 SoC/upstream 场景能力保留。

必学点：

1. ffmpeg 输入输出路径与 hwaccel 基础
2. 像素格式转换成本（CPU copy 与颜色空间转换）
3. 管线瓶颈定位（CPU、内存带宽、IO）

必写代码/实验：

1. RK 板：用 FFmpeg `h264_rkmpp/hevc_rkmpp` 跑真实硬解。
2. RK 板：比较 `h264` 软件路径 vs `h264_rkmpp` 硬件路径指标。
3. VM：可用 `h264_v4l2m2m` 或虚拟 M2M 做框架对照，但不能写成 RK 板硬件结论。
4. 记录失败日志并定位问题环节：command/framework/device/buffer/driver/power。

过关标准：

1. 能给出一份“链路打通说明”
2. 能解释关键瓶颈在什么位置
3. 能复现实验结果（不是一次性跑通）

---

### 阶段 F（Week 11-12）：驱动内核能力（岗位冲刺）

目标：进入“可参与驱动开发”的门槛。

必学点：

1. `v4l2_ioctl_ops`、`v4l2_file_operations`
2. vb2 队列框架（`queue_setup/buf_queue/start_streaming/stop_streaming`）
3. runtime PM、时钟/电源、异常恢复思路
4. 驱动日志与问题复盘方法

必做输出：

1. `VIDIOC_QUERYCAP` 用户态到驱动态调用链说明文档
2. 一个简化驱动回调流程图（文字版即可）
3. 一份“故障注入 -> 恢复策略”清单

过关标准：

1. 能解释“用户态 ioctl 和驱动回调”的对应关系
2. 能看懂并讲解一个真实驱动源码片段
3. 面试时能讲 1 个完整问题闭环（现象-定位-修复-回归）

## 4. 官方文档阅读顺序（防止迷路）

1. userspace-api 总入口

1. driver-api/media/v4l2-core
