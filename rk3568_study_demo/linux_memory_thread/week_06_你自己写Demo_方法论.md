# Week6：你自己写 Demo 的方法论（面向 RK3568 音视频岗）

> 目的：把你从“看别人 demo”切到“自己能做验证闭环”。

## 1. 先纠正一个认知

你不会“凭空发明 demo”。  
真实工程里，demo设计是固定套路：`现象 -> 假设 -> 控制变量 -> 指标 -> 判定标准`。

你缺的不是“天赋”，是“模板”。

---

## 2. 五步模板（每次都照着填）

1. 现象（业务语言）
   - 例：1080p 预览偶发卡顿，平均帧时延不高但体感有顿挫。
2. 假设（技术语言）
   - 例：关键路径有伪共享/随机访问，导致 p99/max 抖动。
3. A/B 设计（只改一个变量）
   - A：packed 计数器
   - B：padded 计数器（64B对齐）
4. 指标（必须量化）
   - throughput、avg/p99/max、deadline_miss、queue_depth
5. 判定标准（提前写）
   - 例：B 相比 A 吞吐提升 >15%，且 p99 下降 >20% 才算有效。

---

## 3. 你立刻可用的“最小实验骨架”

每个实验都应包含：

1. 参数输入（命令行）
2. 时间采样（单调时钟）
3. A/B 两种模式
4. 指标输出（至少 avg+p99+max）
5. 一句结论模板（不写感觉，只写数据）

你仓库里已经有可复用模块：

1. 参数解析：`arg_or_default`
2. 单调时钟：`mono_ns`
3. A/B 对比结构：`run_xxx(mode)`
4. 输出句式：`[MODE] avg=.. p99=.. max=..`

---

## 4. 你最常见的 4 种题型（直接套）

1. 伪共享题
   - 变量：结构布局 packed vs padded
   - 指标：吞吐、CPU占用、p99

2. 局部性题
   - 变量：顺序访问 vs 随机访问
   - 指标：bandwidth、执行耗时

3. 内存抖动题
   - 变量：ON_DEMAND vs PREALLOC_PREFAULT
   - 指标：avg/p99/max/deadline_miss

4. 背压题
   - 变量：队列深度、生产消费速率
   - 指标：push_wait、peak_depth、end-to-end delay

---

## 5. 每次写 Demo 前，用这份清单

1. 我验证的是“正确性”还是“性能”？
2. 只改了一个变量吗？
3. 指标能解释业务体感吗（不只看 avg）？
4. 这个结论能迁移到 RK3568 真链路吗？
5. 有修复前后对比吗？
